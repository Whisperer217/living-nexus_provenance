# Living Nexus — Creator Discovery and Global Player Redesign
## Preservation-first architecture audit

**Date:** 2026-11-06  
**Scope:** Read-only audit and bounded implementation plan  
**Status:** No implementation authorized or performed

## Executive finding

The requested redesign is feasible without rebuilding the Registry, Creator Domains, Works, manifests, media authorization, or playback engine. The current application already has the necessary authorities:

- Explore owns public discovery and creator-directory presentation.
- `profile.allCreators` provides the public creator projection used by the creator view.
- `songs.discoverInfinite` provides cursor-based public Work discovery.
- `CreatorCard` provides an existing contextual creator identity pattern, while Explore currently uses a separate `CreatorDirectoryCard` for the larger directory surface.
- `PlayerContext` is the sole playback and queue authority, backed by one module-level `HTMLAudioElement`.
- `GlobalPlayer` already renders compact, expanded, and cinematic presentation states and routes actions through `PlayerContext`.
- Server-side download permission is enforced in `songs.download`; UI placement must not weaken that gate.

The redesign should therefore be treated as a **presentation and navigation composition project**, not as a new registry, catalog, media, or player system.

## Verified current architecture

### 1. Explore and creator discovery

**Route:** `/explore` in `client/src/App.tsx`.

**Page:** `client/src/pages/ExplorePage.tsx`.

Explore has two explicit modes:

- `list`: public audio Work discovery, supplemental horizontal rows, search, creator filtering, work sorting, randomization, infinite loading, likes, and existing queue handoff.
- `creators`: public creator directory with search, newest/popular sorting, creator filtering, creator cards, and Witnessing actions.

The creator-directory query is:

```ts
trpc.profile.allCreators.useQuery(undefined, {
  staleTime: 5 * 60 * 1000,
  refetchOnWindowFocus: false,
})
```

The public projection currently maps:

- canonical creator `id`
- `name`
- `artistHandle`
- `profilePhotoUrl`
- `bannerUrl`
- `bio`
- `publishedCount`
- `totalPlays`
- `createdAt`
- Stripe account status as an existing support/payout signal

The public creator directory applies client-side search across name, handle, and biography, then sorts by either play count/publication count or creation date. This is suitable for a first additive gallery rail, but the rail should not introduce a second creator query or an independent identity model.

The Work list uses:

```ts
trpc.songs.discoverInfinite.useInfiniteQuery({
  contentType: "audio",
  creatorId,
  limit,
  randomize,
  seed,
  search,
  sort,
})
```

The cursor is the public discovery offset and `nextCursor` is the exhaustion signal. The existing list view already supports Load More behavior and should remain the source of catalog truth.

### 2. Creator identity cards

`client/src/components/CreatorCard.tsx` is an existing contextual identity component. It:

- accepts a canonical numeric `creatorId`
- resolves a small creator projection through `profile.getCreatorMini`
- displays the existing avatar/name and optional founder/work-count/bio/genre context
- links to `/creator/:id`
- has touch-aware opening behavior, viewport clamping, outside-tap dismissal, and a minimum 44px profile action

Explore’s larger directory currently uses its own `CreatorDirectoryCard`, which is appropriate for a gallery card but creates a visual-parity obligation. The proposed redesign should either compose shared identity primitives or align both components to the same card grammar; it should not create a third creator-card pattern.

### 3. Global Player

**Component:** `client/src/components/player/GlobalPlayer.tsx`.

The Global Player currently owns presentation and interaction around the canonical current track. Verified behaviors include:

- context menu actions: Go to Song, View Creator, Share Artifact, Add to My List, Play Next, Download when permitted, and View Songs
- comments drawer with a captured Work target, creator/title display, explicit Switch to Current Track, and draft preservation
- cinematic portal rendered through `createPortal(document.body)`
- cinematic artwork selection separated from playback
- cinematic preview state versus Listening Now state
- explicit Play action routed to `playQueueAt(...)`
- creator continuity and paginated creator-work exploration
- WID verification navigation when a Witness ID is available

The cinematic layer uses a full-screen portal with an artwork atmosphere, vignette, dark fallback, and reduced-motion state. This is already close to the requested Mini / Expanded / Cinematic model. The work should refine its visual language and information hierarchy rather than introduce another player overlay.

### 4. Playback authority

**Component:** `client/src/contexts/PlayerContext.tsx`.

This is the authoritative playback boundary:

- one module-level audio singleton (`_globalAudio`)
- one immutable playback queue snapshot per playback session
- `playQueueAt(...)` starts a new queue and rotates `queueId`
- `addAndPlay(...)` starts a single-track session
- `playNext(...)` inserts into the current session queue
- page navigation does not mutate the active queue
- current track, time, duration, playback readiness, queue context, and session identity are centralized
- session state is restored from `ln_player_session`

Any creator gallery rail or redesign action must call these existing methods. It must never create an `<audio>` element, duplicate queue state, or fetch private media URLs directly.

### 5. Media resolution and download authority

The official download procedure is `songs.download` in `server/routers/songs.ts`.

The server currently:

1. loads the canonical Work by `songId`
2. rejects missing media
3. checks `downloadPermission`
4. requires authentication for all download types
5. checks the tip threshold for `tipped` downloads
6. records the download
7. returns the existing file URL

The Global Player only exposes Download when the current Work projection says a download permission exists, but the server remains authoritative. The redesign must keep download actions confined to the Global Player and individual Work pages as requested, and must not add a creator-gallery download shortcut.

### 6. Routes and identity links

Verified canonical route surfaces:

- `/explore` → `ExplorePage`
- `/creator/:id` → `CreatorProfilePage`
- `/creator/:handle/:medium` → `CreatorCollectionPage`
- `/song/:id` and `/songs/:id` → `SongDetailPage`
- `/track/:id` → canonical track redirect
- `/verify/:witnessId` → `VerifyPage`
- `/playlists` → `PlaylistsPage`
- `/work-desk` → `WorkDeskPage`
- `/creator/collections` → `CollectionsWorkspacePage`

The redesign can add a secondary creator gallery rail beside the existing navigation, but all identity actions must resolve to these canonical paths and preserve numeric creator IDs, handles, Work IDs, and Witness IDs.

## Proposed implementation plan

### Stage A — Shared presentation contract

Create an ADR and define the visual contract before UI edits:

- creator gallery rail is secondary navigation, not a second site hierarchy
- creator context appears below artwork, never as unreadable overlay text
- canonical card grammar uses existing `museum-card`, `museum-pan-row`, typography tokens, and WID/status badge positions
- rail is collapsible on desktop and becomes a horizontal or drawer-based surface on mobile
- all controls have visible focus states, 44px minimum touch targets, and reduced-motion behavior

No schema or API change is required for Stage A.

### Stage B — Additive creator gallery rail

Add one shared rail composition beside the existing LeftRail/MainLayout authority:

- reuse the existing `allCreators` data already available to Explore, or a shared cached query with the same public projection
- use original `profilePhotoUrl`/`bannerUrl` values and canonical creator IDs
- show name/handle and concise metadata below the image
- provide keyboard navigation, collapse/expand, search/filter, and explicit open-profile action
- do not overlay biography or creator context over artwork
- do not add a new creator relationship table

Affected likely files:

- `client/src/components/layout/LeftRail.tsx`
- `client/src/components/layout/MainLayout.tsx`
- a new small shared rail component only if the existing rail cannot compose it cleanly
- `client/src/index.css` for shared tokens/utilities
- `ExplorePage.tsx` only for query/cache reuse if needed

### Stage C — Player presentation refinement

Refine Global Player states without changing PlayerContext:

- Mini: compact current Work identity and essential controls
- Expanded: readable metadata, queue access, comments, collection actions, and permitted download
- Cinematic: current atmosphere/artwork plus explicitly selected preview Work, while audio remains bound to the actual playing Work
- maintain the current explicit Previewing / Listening Now distinction
- use one-panel-at-a-time and bottom-stack rules on mobile
- keep all portals above content but below the documented full-screen overlay layer where appropriate

Affected likely files:

- `client/src/components/player/GlobalPlayer.tsx`
- `client/src/components/player/*` only where an existing subcomponent is already authoritative
- `client/src/contexts/PlayerContext.tsx` only if a type-level presentation hook is genuinely needed; no audio or queue redesign
- `client/src/index.css`

### Stage D — Cross-surface parity

Audit and align creator/work identity treatment across:

- Explore creator cards
- Creator Profile
- Creator Domain
- Work page / Song Detail
- Archive and list rows
- Global Player

The WID remains visible/read-only wherever a Work is represented, and the same CreatorCard/card grammar is reused where the interaction is the same.

### Stage E — Cleanup and retirement decision

Only after adoption and regression evidence:

- measure whether the rail improves creator discovery
- identify duplicated entry points
- retire redundant routes one at a time only with separate approval
- do not delete existing Creator Domain or Studio paths during this redesign

## Database and API impact

**Proposed impact: none.**

No new tables, migrations, WID records, Work records, manifest records, media records, creator relationships, or playback records are needed for the initial redesign.

Potential API work is limited to query reuse or a read-only creator projection optimization if performance evidence requires it. The first implementation should use existing procedures and client caching before adding a new endpoint.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Duplicate creator identity model | Reuse `profile.allCreators`, `CreatorCard`, canonical IDs, and existing routes |
| Gallery rail crowds the main navigation | Make it collapsible; use desktop secondary rail and mobile drawer/horizontal surface |
| Artwork text becomes unreadable | Put creator context below artwork; use explicit metadata rows and contrast tokens |
| Duplicate audio or queue | Enforce PlayerContext-only playback calls in contracts/review |
| Preview selection interrupts listening | Keep cinematic selection state separate from `currentTrackId`; Play remains explicit |
| Download authorization bypass | Keep Download in Global Player/Work page and retain `songs.download` server gate |
| Mobile overlap with player/nav | Apply bottom-stack tokens, portals, solid surfaces, and 390/375/360px validation |
| Visual drift from generic cards | Use existing cathedral tokens and museum-card grammar |
| Query fan-out/performance | Reuse cached creator query; do not fetch per-card catalogs by default |
| Registry/provenance drift | No writes to Works, WIDs, manifests, or historical records |

## Test and validation strategy

Before any checkpoint:

1. `pnpm check`
2. focused Explore, mobile shell, CreatorCard, Global Player, and download contract tests
3. `pnpm test`
4. `pnpm build`
5. `pnpm refine` and confirm the score does not decrease
6. `git diff --check`
7. accessibility checks: keyboard focus, aria labels, reduced motion, touch targets
8. responsive captures at 1440px, 1024px, 768px, 390px, 375px, and 360px
9. playback continuity tests:
   - gallery selection does not start audio
   - explicit Play uses `playQueueAt`/existing authority
   - queue remains unchanged during navigation and preview selection
   - cinematic opening/closing does not create a second audio element
   - mobile player and navigation do not cover final list items
10. permission tests:
   - public creator discovery remains public
   - private/withdrawn Works do not appear through new surfaces
   - Download remains unavailable unless the server-side permission gate allows it
   - WID links resolve to the existing Verify route

## Rollback strategy

Because the proposed first stages are presentation-only:

- revert the dedicated implementation commit or checkpoint
- leave database schema and records untouched
- leave media and manifests untouched
- leave PlayerContext and playback queue behavior untouched
- retain old navigation and Creator Domain routes
- if the new rail causes mobile regression, disable the rail behind its presentation flag or revert the rail component while keeping the existing LeftRail intact
- do not use rollback as a reason to rewrite or restore production data; no production data should be changed by this work

## Decision gate

**Recommendation: CONDITIONAL GO for Stage A design and Stage B additive prototype only.**

Approval should explicitly cover:

- the secondary creator rail as a presentation layer
- reuse of existing creator and Work procedures
- no database or Registry changes
- no second playback authority
- no download expansion
- visual validation before checkpoint

Do not proceed to Stage C cross-surface player refinement or Stage E route retirement until the Stage B prototype has passed responsive, accessibility, and playback-continuity validation.
